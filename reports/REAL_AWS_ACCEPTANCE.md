### Expiry method, not a natural-duration claim

Only this run's new application connection `9475432e-cf9e-4bd1-bf75-a07347399370` had its database `expires_at` moved into the past using a scoped operator command. No global TTL, AWS key or browser's separate working connection was changed. Listing/import through that expired connection returned 410; already imported CSV and Excel snapshots completed new transformations, and their original next-day expiry timestamps remained unchanged.

This validates expiry enforcement and lifetime independence during the 24-hour window. It does **not** mean that one hour was waited, an AWS STS token naturally expired, or the snapshots were continuously observed for 24 hours. Those duration/STS cases remain NOT RUN.

### Controlled retry method, not an observed AWS outage

`scripts/inject_acceptance_retry.py` created one new inspect job for this test session, after checking that session had no active jobs and obtaining a genuine AWS object fingerprint. In that isolated operator Python process only, the first `import_source` call raised retryable `S3_TEMPORARY_ERROR`. The normal task handler persisted attempt 1 / RETRYING and a real outbox entry. That process exited; normal dispatcher/Celery performed attempt 2, downloaded genuine AWS bytes and completed Spark. Its snapshot SHA-256 matched the uploaded CSV.

No successful AWS response, model output or Spark output was mocked. No production service, network rule or running worker module was disrupted. The first injected attempt was run by the operator harness, not initially dispatched from the browser. This is controlled recovery evidence, **not** a naturally observed AWS outage or a claim of every possible recovery failure mode.
